# AGENTS.md — shortnr

URL shortener with a dashboard, CLI, MCP server, and AI insights. ASP.NET Core Razor Pages + HTMX, EF Core (multi-provider), feature-module architecture.

## Project state

Nine projects under `src/` and `tests/`:
- **Shortnr.Data** — class library: entities (`ShortenedUrl`, `ShortenedUrlMetadata`, `ShortenedUrlTag`, `TagSuggestion`, `ClickEvent`, `User`, `ApiKey`, `Domain`, `BioPage`, `BioPageLink`, `AiActivityLog`, `Workspace`, `WorkspaceMember`, `Webhook`, `PixelSnippet`), `AppDbContext`, EF Core migrations (SQLite-flavored, the default provider), `DatabaseProviderHelper` + `DatabaseProvider` enum, `IDesignTimeDbContextFactory<AppDbContext>` for `dotnet ef`. Multi-provider via `Database:Provider` (default `Sqlite`; `Postgres` supported).
- **Shortnr.Data.Postgres** — class library holding only the Postgres-flavored EF Core migrations for `AppDbContext` (its own migration history/snapshot, scaffolded against Npgsql). `DatabaseProviderHelper.UseProvider`'s `Postgres` branch selects this assembly via `.MigrationsAssembly("Shortnr.Data.Postgres")`. Kept separate from `Shortnr.Data`'s SQLite migrations because `Database.Migrate()` replays a migration's frozen `Up()`/`Down()` operations verbatim — it can't derive Postgres-native DDL (column types, identity/sequence generation) from a SQLite-scaffolded history, and the two providers can't share one migration history for the same `DbContext` out of one assembly. `Shortnr.Web` references this project purely so the DLL is deployed to the app's output folder for `Assembly.Load` to find at runtime — nothing calls it directly in code.
- **Shortnr.Web** — ASP.NET Core Razor Pages (`Pages/`) + minimal API endpoints. Feature modules live in `Features/<Feature>/`, each owning its own DI composition boundary via `Add<Feature>Feature()` extension methods wired together in `Program.cs`. See "Feature modules" below. OIDC login/signup wired against a test IdP (Dex); API keys + OAuth 2.1 server (OpenIddict) are separate bearer-auth schemes for the REST API and the MCP endpoint. Auth is opt-in via `Authentication:Enabled`.
- **Shortnr.Cli** — AOT-published CLI (`shortnr-cli`) wrapping the `/api/v1` REST API. Shorten/list/stats/delete. Config via `SHORTNR_API_KEY`/`SHORTNR_BASE_URL` env vars or `~/.shortnr/config`. Publish with `dotnet publish src\Shortnr.Cli\Shortnr.Cli.csproj -c Release -r <RID> --self-contained true` (AOT requires clang/gcc).
- **Shortnr.AppHost** — .NET Aspire 13.4 orchestrator for local dev: runs `Shortnr.Web` plus Dex and MailPit containers, and (when `docs/` exists) the Astro docs dev server as a `shortnr-docs` Vite app resource. Wires `Authentication__Oidc__Authority`, `Smtp__Host/Port`, and `Database__Provider` into the web app; provisions a Postgres container when `Database:Provider`/`db-provider` is set to `Postgres`, on a named data volume (`shortnr-postgres-data`) so local troubleshooting data survives container recreation. The `IsTestRun` config flag (default `false`) skips the Dex/MailPit containers and switches the Postgres resource to a separate name + volume (`postgres-test` / `shortnr-postgres-test-data`) — used by `PostgresAppHostFixture` (see Testing conventions) so the test suite never shares data with, or resets, the local dev database; leave it unset for real dev work. See the `aspire` skill (`.claude/skills/aspire`).
- **Shortnr.ServiceDefaults** — shared `AddServiceDefaults()`/`MapDefaultEndpoints()` (health checks, OpenTelemetry, service discovery) referenced by `Shortnr.Web`.
- **Shortnr.Tests.Unit** (`tests/`) — xUnit unit tests for services (no HTTP stack, EF Core InMemory).
- **Shortnr.Tests.Integration** (`tests/`) — xUnit integration tests using `WebApplicationFactory<Program>` with a real SQLite DB and `TestAuthHandler` that replaces OIDC.

`dex/config.yaml` configures the Dex test IdP — see the `dex-oidc` skill (`.claude/skills/dex-oidc`) before editing it or `Shortnr.Web`'s `Authentication:Oidc:*` config. Two test users are provisioned (`test@example.com` and `test2@example.com`, both password `password`) for multi-user workspace testing.

## Dev commands

- **Build**: `dotnet build` (repo root) — also runs `libman restore` automatically via `Microsoft.Web.LibraryManager.Build`.
- **Test**: `dotnet test` (repo root) — runs both unit and integration test projects. The Postgres parity suite (`Category=Postgres`) runs as part of this but degrades to skipped, not failed, on a machine without Docker — see Testing conventions.
- **Run standalone** (no auth, no IdP): `dotnet run --project src\Shortnr.Web\Shortnr.Web.csproj`. Auth is **enabled by default** in `appsettings.json`; pass `Authentication:Enabled=false` to disable it without an IdP.
- **Run under Aspire** (Dex + MailPit, requires a container runtime): `dotnet run --project src\Shortnr.AppHost\Shortnr.AppHost.csproj --` — wrapper-less form avoids argument forwarding issues; the Aspire dashboard URL is printed to the console.
- **Add SQLite migration**: `dotnet ef migrations add <Name> --project src\Shortnr.Data\Shortnr.Data.csproj` (run from repo root so the startup project resolves).
- **Remove SQLite migration**: `dotnet ef migrations remove --project src\Shortnr.Data\Shortnr.Data.csproj`.
- **Add Postgres migration**: scaffold against a real Postgres (e.g. via `aspire run` with `db-provider=Postgres` — see the `aspire` skill), then `dotnet ef migrations add <Name> --project src\Shortnr.Data.Postgres\Shortnr.Data.Postgres.csproj --startup-project src\Shortnr.Web\Shortnr.Web.csproj --context AppDbContext` with `Database__Provider=Postgres` / `Database__ConnectionString=<...>` set in the environment.
- **Restore frontend assets manually**: `cd src\Shortnr.Web && libman restore` (requires `dotnet tool install -g Microsoft.Web.LibraryManager.Cli`).
- **Docs**: `cd docs && npm run dev` (Astro 5, Starlight content; Node ≥ 20). `npm run check` typechecks. `npm run build` for the deploy (`docs-deploy.yml`).

> A running `Shortnr.Web` or `Shortnr.AppHost` process locks `bin\` outputs and makes `dotnet build` fail with `MSB3027`/`MSB3021` file-copy errors. Stop it (or check for the PID in the error message) before building/testing.

## Feature modules (`src/Shortnr.Web/Features/`)

Program.cs wires 15 feature modules together; each owns its own DI composition and lives under `Features/<Feature>/` with an `Add<Feature>Feature()` extension:

- **ShortLinks** — `ShortLinkCodes`, `QrService` (singleton, wraps QRCoder, `/qr/{code}` page + `/api/qr/{code}` PNG), `ShortenRateLimiter`, `PixelSnippetRenderer`, `ViewRenderService` (the approved way to render a `.cshtml` partial from a minimal-API endpoint — used only for the pixel interstitial; do **not** use it to dodge the "no inline HTML" rule on Razor-Pages surfaces), `LinkEndpoints` (redirect).
- **ClickTracking** — `Channel<ClickRecord>` + `ClickBatchProcessor` background service. Redirect endpoint writes to the channel and returns immediately; the processor batch-updates the DB.
- **Authentication** — `UserIdentityService` (scoped, centralises `IsAuthEnabled` + `ResolveOwnerUserIdAsync` + `ResolveActiveWorkspaceContextAsync`; `IUserIdentityService` is the abstration injected into handlers — never resolve owner/workspace inline in a page model), `ApiKeyService` (`snr_`-prefixed keys, SHA-256 hash persisted only), `ApiKeyHandler`, `ApiKeyScopes` (`links:read`/`links:write`/`mcp:read`/`mcp:write`; empty-stored-scope = full access for backward compat), `UserProvisioningProcessor` (queued upsert via `Channel<PendingUserLogin>`; the request path never blocks on a DB write), `AuthenticationServiceExtensions` / `AuthenticationEndpointExtensions` (both no-ops when `Authentication:Enabled=false`). Never add IdP-specific code to `Shortnr.Web` — swapping the upstream IdP is a `dex/config.yaml` change only.
- **Domains** — branded `Domain` entity (`Hostname`, `IsVerified`, `IsDefault`, `VerificationToken`), verification via well-known file or DNS TXT. `MakeDefaultAsync` migrates the owner's existing `DomainId == null` links onto the new default and skips collisions.
- **Workspaces** — `Workspace` (slug-keyed) + `WorkspaceMember` (`WorkspaceRole` enum: Owner=2/Editor=1/Viewer=0, `InviteEmail` for pending invites). A link or domain has exactly one of {personal owner, workspace}. Active workspace resolved from the `snr_workspace` cookie by `UserIdentityService.ResolveActiveWorkspaceContextAsync`. `WorkspaceAuthorizationService` is the single role-enforcement gate. Pending invites auto-accepted on next OIDC login by `UserProvisioningProcessor` matching email claims. Invite emails via the `Email` module to the MailPit container. Switch endpoint `POST /workspace/switch`. Dashboard, Index, `/api/metrics`, Domains and Bio Edit pages are all workspace-scoped (exclusive — when a workspace is active, personal links are excluded). `AiActivityLog` stays personal-only. **Workspaces require auth to be enabled.**
- **BioPages** — personal bio page editor (`/bio/edit`) and public page (`/bio/{slug}`) with theme picker, link reordering, avatar.
- **Api** — versioned REST CRUD at `/api/v1/links` + `/links/{code}/clicks` (`ApiV1Endpoints.cs`). Whole group requires the `ApiKey` policy and the `api-key` rate-limiter. `CreateLinkAsync` accepts an optional `Domain` (must be owned + verified); omitted it falls back to the owner's default domain. OpenAPI is restricted to `api/v1*` paths; Scalar UI at `/api/docs`. Per-key scopes (`links:read`/`links:write`) enforced via the policy.
- **Mcp** — `/mcp` endpoint (ModelContextProtocol.AspNetCore). Tools in `McpTools/` are split into link read/write, bio read/write, and system. Auth: API key (`mcp:read`/`mcp:write` scopes) **or** OAuth 2.1 access tokens (validated by OpenIddict). Protected-resource metadata served per RFC 9728. `McToolGuard` enforces per-tool read/write granularity from the principal's scope claims.
- **OAuth** — OpenIddict-based OAuth 2.1 authorization server for MCP clients (`OAuthServerExtensions`, `OAuthModule`). `OAuth:Issuer` must be the real `https://` URL in production. **Requires_pkcs#12 signing + encryption certificates outside `Development`** (`OAuth:SigningCertificate`/`OAuth:EncryptionCertificate`, base64) — see the docs `mcp.md` page for generation steps. Scopes are seeded at startup via `OAuthServerExtensions.EnsureOAuthScopesAsync`.
- **Webhooks** — `Webhook` entity (url, secret, space-separated event types), `WebhookEventDispatcher` + `WebhookDeliveryService` (queued fire-and-forget delivery), `WebhookSigningService` (HMAC-SHA256 signature header), `WebhookUrlValidator`. Event types: `link.created`, `link.clicked`, `link.deleted`. Managed at `/settings/webhooks`.
- **Email** — MailKit SMTP (fire-and-forget); host/port wired by the AppHost to MailPit.
- **GeoIp** — optional MaxMind GeoLite2 enrichment. **Disabled (fails open) until both `GeoIp__MaxMindAccountId` and `GeoIp__MaxMindLicenseKey` are set.** Database downloaded at startup and on Wed/Sat 12:00 UTC; never bundled with the repo. Footer attribution is required by the GeoLite2 EULA.
- **AiActivity** — `AiActivityLog` records MCP tool actions performed on behalf of a user; surfaced at `/dashboard/activity` (`Pages/Dashboard/Activity.cshtml.cs`). Personal-only (no workspace FK). `AiActivityProcessor` drains a channel like the other background services.
- **Insights** — `AiInsightsHostedService` runs on a configurable schedule (`AiInsights:AnalysisIntervalHours`, default 24h, min 10 clicks); `InsightHeuristics` generates suggestions surfaced at `/insights`. Personal data only.
- **Infrastructure** — `ChainedRateLimiter`, `ClientIpResolver`, `RateLimitingOptions`, `GravatarHelper` (MD5 email hash, mystery-person fallback, used by `Pages/Shared/_UserMenu.cshtml`).

## Architecture & conventions

- **Razor partials for HTMX responses** — PageModel handlers that respond to HTMX must use `Partial("Shared/_PartialName", model)` (returns `PartialViewResult`); full-page responses use `Page()` with layout. Never build HTML inline in C# (no raw strings, no `Content()` with HTML). The only sanctioned exception is `ViewRenderService` in `Features/ShortLinks`, used by the minimal-API redirect endpoint to render the pixel interstitial partial — not a general-purpose escape hatch on Razor-Pages surfaces. Never manually construct `PartialViewResult` or assign a different model to `ViewData.Model`.
- **HTMX header check** — `Request.Headers["HX-Request"].Count > 0` for full-page vs partial. On POST handlers, `Partial()` returns the partial. For multiple partial targets on the same page (e.g., dashboard metrics + search), branch on `Request.Headers["HX-Target"].FirstOrDefault()` (the swapped element's `id`) instead of polluting `OnGet` with routing query parameters.
- **Backend services are background `Channel<T>`+`BackgroundService` processors** — click tracking, user provisioning, AI activity, webhook deliveries, AI insights all follow the same pattern. New async work should mirror it rather than blocking the request path.
- **Migrations are additive** — never delete or rewrite a committed migration (`src/Shortnr.Data/Migrations/` for SQLite, `src/Shortnr.Data.Postgres/Migrations/` for Postgres — separate histories, see the `Shortnr.Data.Postgres` bullet above). Database auto-migrated at startup via `db.Database.Migrate()` in `Program.cs`; OAuth scopes seeded in the same block.
- **DbContext** is injected via DI and resolved lazily inside the `AddDbContext` options callback (so test-host `ConfigureAppConfiguration` overrides win — do not resolve the connection string eagerly at the top of `Program.cs`). `AppDbContext.StampTimestamps` auto-sets `CreatedAtUtc` on added entities.
- **Short code / slug rules** — 6 alphanumeric chars via `ShortLinkCodes.GenerateCode()`; vanity slugs are 1–64 chars of `[a-zA-Z0-9_-]` starting with a letter/digit (`ShortLinkCodes.IsValidSlug`). Both the Index page and `/api/v1` use `ShortLinkCodes` — never duplicate slug rules elsewhere. Codes are unique per domain (`DomainId, ShortCode` composite unique index); `DomainId == null` means the instance's own host. The unique index is filtered (`"DomainId" IS NOT NULL` / `"DomainId" IS NULL`, ANSI double-quote syntax — valid on Sqlite and Postgres).
- **Host-aware redirect** — `GET /{shortCode}` (in `Features/ShortLinks/LinkEndpoints.cs`) looks up the link by `(host, shortCode)`: a verified domain matching the request host resolves `DomainId == domain.Id`, otherwise it falls back to the instance's `DomainId == null` links. Same code can exist on different domains.
- **Solution format** — `.slnx` (the .NET 10 XML-based format). Target framework `net10.0` across all projects.
- **Frontend stack** — Pico CSS v2, htmx v2, Alpine.js v3, Chart.js v4 — all served locally from `wwwroot/lib/` (gitignored, restored at build by LibMan). See `src/Shortnr.Web/libman.json` for pinned versions. Both `pico.min.css` and `pico.colors.min.css` loaded in `_Layout.cshtml`. No npm, no bundler in the web app (npm is only used by `docs/`).
- **Status colors via Pico classes** — `pico-background-red-100` (errors), `pico-background-green-100` (success/verified/active), `pico-background-blue-100` (informational). No custom color style tags.
- **Alpine.js + Chart.js**: loaded only on the Dashboard page. Chart.js polls `/api/metrics` every 5s via Alpine `setInterval`; `#metrics-summary` HTMX region polls `/dashboard` every 5s. Search queries `/dashboard` with `HX-Target: search-results`.
- **Nav user menu** — uses Pico's native `<details class="dropdown">` pattern (no custom dropdown CSS), includes the workspace switcher as dropdown forms. `_UserMenu.cshtml` reads claims from the current principal.
- **Dashboard access control** — when auth is enabled, unauthenticated full-page requests to `/dashboard` redirect to `/`; unauthenticated HTMX partial requests return `401` (so the browser doesn't silently swap the page with a login redirect mid-poll). The Dashboard link is hidden in the nav when auth is enabled and the user is not signed in.
- **Dashboard data scoping** — all three dashboard query branches (metrics summary, recent clicks, search/link list) filter by `OwnerUserId` when auth is enabled, or by `WorkspaceId` when a workspace is active. `/api/metrics` returns zeros for anonymous requests when auth is enabled rather than leaking all records. Workspace scoping is exclusive.
- **Dashboard domain filter** — search/link list filters by `domain` query param: `default` means `DomainId == null`, otherwise matches the verified domain hostname. Filter options come from `LoadDomainOptionsAsync`.
- **Rate limiting** — three policies wired in `Program.cs`. `ChainedRateLimiter` (`Features/Infrastructure`) stacks two fixed windows per key: `api-key` (60/min + 1000/day, partitioned by hashed bearer key), `mcp-tools` (120/min + 5000/day, same key partitioning so REST and MCP share a budget), and `redirect-ip` (per-IP, configurable via `RateLimiting:Redirect:*`, deliberately generous). The shorten form is gated by `ShortenRateLimiter` per config `RateLimiting:Shorten:*`. Trusting `X-Forwarded-For` / `X-Forwarded-Proto` is opt-in via `RateLimiting:TrustForwardedFor` and `Hosting:TrustForwardedHeaders` — only enable behind a proxy you control.
- **Provider swap** — `Database:Provider` + `Database:ConnectionString` config. `Sqlite` and `Postgres` are the only supported values; anything else throws at DI build time.
- **Data Protection key ring** — persisted to a configured volume path (`DataProtection:KeyPath`) so auth cookies and OIDC correlation cookies survive redeploy. Do not remove that wiring without a replacement, or you'll silently log users out on every cold start.
- **Ownership best-effort** — `ShortenedUrl.OwnerUserId` is set from the current principal at creation; it may be `null` for a user's very first link if the provisioning queue hasn't written their `Users` row yet. Do not duplicate the upsert on the request path to "fix" this.

## Testing conventions

- Unit tests in `tests/Shortnr.Tests.Unit/` — service logic, EF Core InMemory, no HTTP stack.
- Integration tests in `tests/Shortnr.Tests.Integration/` — `WebApplicationFactory<Program>` with `ShortnrWebAppFactory` (isolated SQLite DB per test class by default; auth overridden with `TestAuthHandler`).
- Control auth state in integration tests via `factory.Services.GetRequiredService<TestAuthState>().SetAuthenticatedUser(...)`. Never test real OIDC flows — those require a running IdP and are E2E territory.
- API-key auth tests (`ApiV1EndpointsTests`) seed a `User` + `ApiKey` row directly and send `Authorization: Bearer <plaintext>` — `ApiKeyService.HashKey` must match what `ApiKeyHandler` computes. Domain verification tests (`DomainsSettingsTests`) stub `DomainVerifierService` via `ConfigureTestServices` with a fake HTTP handler serving tokens by hostname.
- `public partial class Program { }` at the bottom of `Program.cs` (line 275) is required for `WebApplicationFactory<Program>` to compile — keep it.
- **Postgres parity suite** (`Data/DatabaseProviderParityTests.cs`, `[Trait("Category", "Postgres")]`) is a focused set of `[SkippableTheory]` tests covering behavior that genuinely differs by provider (the filtered unique index, timestamp stamping, one create→redirect round trip) — not a replacement for the broader single-provider suite, which stays SQLite-only. `PostgresAppHostFixture` provisions Postgres for real via `DistributedApplicationTestingBuilder` against the actual AppHost (`db-provider=Postgres`, `IsTestRun=true`), which requires the integration test project's `Aspire.Hosting.Testing` package + aliased `ProjectReference` to `Shortnr.AppHost` (aliased as `ShortnrAppHost` — both projects' top-level-statement `Program.cs` otherwise collide on the implicit global `Program` type). `IsTestRun=true` also switches the AppHost's Postgres resource to a separate name/volume (`postgres-test` / `shortnr-postgres-test-data`) so this suite's data never collides with the local dev database. Run just this suite with `dotnet test --filter "Category=Postgres"` (requires Docker); it degrades to skipped rather than failed when Docker isn't reachable, so a bare `dotnet test` still passes without one. `ci.yml`'s `test-postgres-parity` job runs it on every PR/push to main — there is no separate nightly Postgres workflow.

## Multi-feature workflow (stacked PRs with gh-stack)

**Whenever dealing with multiple features at a time, use `gh stack`** — one stack per project, one layer (branch → PR) **per feature** (e.g. `feat/auth` → `feat/api-keys`). Each PR targets the branch below it, so reviewers see only that feature's diff. Do not open one giant PR, pile unrelated features onto a single branch, or split one feature across multiple branches.

- **Commits are the units of work, not branches.** Each feature layer is built from multiple logical commits (data model → migration → services → UI → tests), one commit per logical unit. Do not squash a feature into a single commit.
- The `gh stack` extension (`github/gh-stack`) is installed; see the `gh-stack` skill (`.agents/skills/gh-stack`) for the full non-interactive workflow, command reference, and exit-code handling.
- Branch names use the repo's existing `feat/...` convention verbatim; plan layers in dependency order (foundational features lowest) before running `gh stack init`.
- One-time git config (avoids interactive prompts): `git config rerere.enabled true` and `git config remote.pushDefault origin` (single `origin` remote).
- **All `gh stack` commands must run non-interactively** or they hang: always pass branch names to `init`/`add`/`checkout`, `--auto` to `submit`, `--json` to `view`, `--yes` to `merge`.
- Standard loop: `gh stack init feat/<first-feature>` → per feature, commit logical units then `gh stack add feat/<next-feature>` → `gh stack submit --auto` → keep layers rebased with `gh stack sync` (or navigate down, commit, `gh stack rebase --upstack`) → **a human reviews every PR** and only then the stack is merged.
- **Stacks are never auto-merged and never merged in the same session that creates them.** Only merge with `gh stack merge <n> --yes [--squash]` on the human's explicit request. Never use `gh pr merge` on stacked PRs; never commit unrelated features into an open stack.
